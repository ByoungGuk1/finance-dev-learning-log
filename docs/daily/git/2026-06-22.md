## 2. GitHub 협업 흐름

GitHub 협업은 로컬 Git 명령만으로 끝나지 않고, 원격 저장소를 기준으로 작업 흐름을 맞추는 과정이다.

기본 흐름은 다음과 같다.

```text
원격 저장소 clone
→ 브랜치 생성
→ 기능 개발
→ commit
→ push
→ Pull Request 생성
→ 리뷰 및 merge
```

---

## 3. 브랜치 전략

실습에서는 `main`, `develop`, `feature`, `conflict` 계열 브랜치를 사용했다.

```text
main: 안정적인 기본 브랜치
develop: 기능을 모으는 개발 브랜치
feature/A, feature/B: 기능 개발 브랜치
conflict/A, conflict/B: 충돌 실습 브랜치
```

기능 개발은 직접 `main`에 하지 않고 별도 브랜치에서 진행한다.
이렇게 하면 기능 단위로 변경사항을 확인할 수 있고, 문제가 생겨도 기본 브랜치를 보호할 수 있다.

---

## 4. Pull Request

Pull Request는 내 브랜치의 변경사항을 다른 브랜치에 합쳐달라고 요청하는 과정이다.

PR에서 확인하는 내용은 다음과 같다.

- 어떤 파일이 바뀌었는지
- 어떤 코드가 추가/삭제되었는지
- 기능 의도와 테스트 방법이 명확한지
- 충돌이 발생하는지

수업 자료에서는 PR 본문에 다음 정보를 정리하는 흐름을 다뤘다.

```text
작업 내용
기존 코드와의 연관성
테스트 방법
리뷰 포인트
```

---

## 5. 충돌 해결

충돌은 두 브랜치가 같은 파일의 같은 위치를 다르게 수정했을 때 발생한다.

실습에서는 `BoardService.java`의 `findAll()` 메서드에 A/B 버전 로그를 다르게 추가하면서 충돌 상황을 만들었다.

충돌 파일에는 다음과 같은 마커가 생긴다.

```text
<<<<<<< HEAD
현재 브랜치 내용
=======
병합하려는 브랜치 내용
>>>>>>> branch-name
```

해결할 때는 마커를 지우고 최종 코드만 남긴 뒤 다시 커밋한다.

```bash
git add BoardService.java
git commit -m "merge: 충돌 해결"
```

## 6. Revert

잘못 merge된 내용을 되돌릴 때는 `revert`를 사용할 수 있다.

`reset`은 이력을 되감는 방식이고, `revert`는 이전 변경을 취소하는 새 커밋을 만드는 방식이다.
협업 저장소에서는 다른 사람의 이력과 충돌하지 않도록 `revert`가 더 안전하다.

## 7. 실습 코드 기준 정리

`board-practice` 레포에서는 다음 파일들이 Git 실습 대상으로 사용되었다.

```text
Board.java
BoardService.java
BoardRepository.java
BoardValidator.java
Login.java
README.md
```

이 코드들은 완성된 게시판 애플리케이션이라기보다, Git 변경사항을 만들기 위한 실습용 코드로 보는 것이 맞다.

## 8. 다시 볼 부분

- feature 브랜치를 develop 기준으로 만드는 이유
- PR을 통해 merge하는 이유
- 충돌이 난 파일에서 마커를 제거하는 방식
- `git fetch --prune`으로 삭제된 원격 브랜치 캐시를 정리하는 이유
- `revert`와 `reset`의 차이

## 정리

오늘 정리는 GitHub 협업 흐름을 실제 브랜치와 PR 중심으로 이해하는 데 초점을 둔다.
혼자 사용하는 Git에서는 commit/push 정도가 중요하지만, 협업에서는 브랜치 기준, PR 리뷰, 충돌 해결, merge 이후 브랜치 정리까지 함께 이해해야 한다.
