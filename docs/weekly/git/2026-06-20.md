## 2. 이번 주 핵심 흐름

이번 구간은 Git을 단순 저장 도구가 아니라 **협업 이력을 관리하는 도구**로 사용하는 흐름을 다뤘다.

핵심 흐름은 다음과 같다.

```text
작업 파일 수정
→ git add
→ git commit
→ git push
→ GitHub Pull Request
→ 코드 리뷰
→ merge
```

---

## 3. Git 기본 개념

Git은 파일의 변경 이력을 커밋 단위로 저장한다.

| 개념 | 의미 |
|---|---|
| Working Tree | 실제 파일을 수정하는 작업 공간 |
| Staging Area | 커밋할 파일을 올려두는 임시 공간 |
| Repository | 커밋이 저장되는 저장소 |
| Commit | 변경사항을 저장한 하나의 이력 |
| Branch | 독립적인 작업 흐름 |
| Merge | 다른 브랜치의 변경사항을 합치는 작업 |

기본 명령 흐름은 다음과 같다.

```bash
git status
git add .
git commit -m "message"
git push origin branch-name
```

## 4. GitHub 협업 흐름

수업 자료에서는 GitHub를 사용한 브랜치 전략과 Pull Request 흐름을 다뤘다.

```text
main
└── develop
    ├── feature/A
    └── feature/B
```

각 작업자는 feature 브랜치에서 기능을 개발하고, Pull Request를 통해 develop 브랜치로 병합한다.

이 방식의 장점은 다음과 같다.

- main/develop 브랜치를 직접 수정하지 않음
- 기능 단위로 작업 이력을 분리할 수 있음
- PR에서 변경 내용을 확인하고 리뷰할 수 있음
- 충돌이 발생한 경우 병합 전에 해결할 수 있음

## 5. 실습 레포 흐름

`git-practice.zip`의 `board-practice` 레포는 게시판 예제 코드를 이용해 Git 협업 흐름을 연습한 자료다.

확인된 주요 커밋 흐름은 다음과 같다.

```text
feat: Board Class 추가
feat: reset --mixed 연습
feat: Board3.java 복제
feat: Board3.java 수정
docs : add README.md
feat: BoardService 기본 구조 추가
feat: Board 조회수(viewCount) 기능 추가
feat: BoardValidator 입력값 검증 추가
refector: Board.java 수정
feat: 이슈 생성 후 브랜치 만들어 작업
feat: BoardService 삭제 및 수정 기능 추가
feat: BoardRepository Optional 패턴 적용
feat: findAll 로그 추가 (A버전)
Revert "feat: findAll 로그 추가 (A버전)"
```

실습 내용은 컴파일 가능한 게시판 프로젝트 완성보다는 **브랜치, PR, 충돌, revert를 경험하는 목적**에 가깝다.

## 6. 브랜치 실습

`feature/A`, `feature/B`, `conflict/A`, `conflict/B` 같은 브랜치를 사용해 작업 흐름을 분리했다.

예시로 `feature/A`에서는 `Board`에 조회수 기능을 추가했다.

```java
private int viewCount = 0;
public int getViewCount() { return viewCount; }
public void incrementViewCount() { this.viewCount++; }
```

`feature/B`에서는 `BoardService`의 삭제/수정 기능과 `BoardRepository` 구조를 추가했다.

## 7. 충돌 실습

충돌은 같은 파일의 같은 위치를 서로 다르게 수정했을 때 발생한다.

수업 자료에서는 `BoardService.java`의 `findAll()` 부분을 A/B 버전에서 서로 다르게 수정하는 방식으로 충돌을 만들었다.

충돌 해결 흐름은 다음과 같다.

```bash
git status
# 충돌 파일 직접 수정
# <<<<<<<, =======, >>>>>>> 마커 제거
git add BoardService.java
git commit -m "merge: 충돌 해결"
```

충돌 해결에서 중요한 점은 Git이 자동으로 정답을 고르는 것이 아니라, 개발자가 최종 코드를 직접 결정해야 한다는 점이다.

## 8. Revert

Git 실습에서는 잘못 merge한 PR을 되돌리는 `revert` 흐름도 확인했다.

`reset`은 이력을 되감는 느낌이고, `revert`는 되돌리는 커밋을 새로 만들어 이력을 보존한다.
협업 중인 원격 저장소에서는 보통 `revert`가 더 안전하다.

- `branch`와 `checkout/switch`의 차이
- `merge`와 `rebase`의 차이
- PR을 왜 사용하는지
- conflict 마커를 제거하고 최종 코드를 선택하는 과정
- `reset`과 `revert`의 차이
