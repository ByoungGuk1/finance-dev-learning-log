# 체크카드 온라인 결제 프로세스 정리

## 1. 한 줄 정리

체크카드 온라인 결제는  
사용자가 온라인 결제창에서 체크카드를 선택하고 본인 인증을 거친 뒤,  
PG사가 카드사로 승인 요청을 보내고,  
승인 성공 시 연결된 결제계좌에서 금액이 즉시 출금되는 결제 흐름이다.

체크카드는 신용카드처럼 일정 기간 뒤에 청구되는 구조가 아니라, 일반적으로 카드 이용 즉시 결제가 이루어진다는 점에서 신용카드와 구분된다.

## 2. 체크카드 온라인 결제란?

온라인 쇼핑몰에서 체크카드로 결제할 때 사용자는 결제창에서 카드 정보를 입력하거나 카드사 앱 인증을 진행한다.

이후 PG사는 카드사 또는 결제망을 통해 카드 승인 요청을 보내고, 카드사는 카드 상태, 연결 계좌 잔액, 이용 가능 여부 등을 확인한 뒤 승인 또는 거절 결과를 반환한다.

체크카드는 신용카드와 달리 승인 시점에 연결 계좌에서 금액이 바로 출금될 수 있다.  
따라서 체크카드 온라인 결제에서는 `승인 성공`, `즉시 출금`, `환불 지연 가능성`을 함께 이해해야 한다.

## 3. 전체 프로세스 흐름

```text
사용자 주문 생성
  → 온라인 결제창 호출
  → 체크카드 선택
  → 카드 본인 인증
  → PG 결제 인증 결과 반환
  → 가맹점 서버가 결제 승인 API 호출
  → PG / VAN / 카드사 승인 처리
  → 결제계좌 잔액 확인 및 즉시 출금
  → 결제 성공 처리
  → 주문 상태 변경
  → 매입 / 정산
  → 취소 요청 시 취소 / 환불 처리
```

카드 결제는 크게 인증, 승인, 매입 단계로 설명할 수 있다.  
인증은 카드 소유자 확인, 승인은 결제 가능 여부 확인, 매입은 승인된 결제 건을 카드사에 알려 정산을 받는 과정이다.

체크카드는 이 중 승인 단계에서 신용카드와 차이가 크다.  
신용카드는 승인 시점에 한도가 차감되고 나중에 청구되지만, 체크카드는 승인 시점에 연결 계좌에서 금액이 바로 출금될 수 있다.

## 4. 단계별 설명

### 1단계. 주문 생성

온라인 쇼핑몰 서버는 사용자가 결제하기 전에 주문 데이터를 먼저 만든다.

이때 보통 다음 정보를 저장한다.

| 항목     | 설명                             |
| -------- | -------------------------------- |
| 주문번호 | 쇼핑몰 내부 주문 식별값          |
| 주문금액 | 실제 결제되어야 하는 금액        |
| 상품명   | 결제 대상 상품 정보              |
| 회원정보 | 주문자 또는 구매자 정보          |
| 주문상태 | 결제 전, 결제 요청, 결제 완료 등 |

이 단계에서 주문 상태를 바로 `결제 완료`로 두면 안 된다.  
아직 결제가 승인된 것이 아니기 때문이다.

사용할 수 있는 예시 상태값은 다음과 같다.

```text
ORDER_CREATED
PAYMENT_REQUESTED
PAYMENT_APPROVED
PAYMENT_FAILED
PAYMENT_CANCELED
```

결제 시스템에서는 내부 주문 식별값인 `orderId`를 반드시 관리해야 한다. PG사 결제 결과와 내부 주문을 연결해야 하기 때문이다.

<sub>출처: [5]</sub>

### 2단계. 온라인 결제창 호출

사용자가 결제 버튼을 누르면 프론트엔드는 PG사의 결제창을 호출한다.

결제창에서는 사용자가 결제수단을 선택하고, 카드 정보를 입력하거나 카드사 앱 인증을 진행한다.  
체크카드 온라인 결제도 일반적으로 신용카드 결제와 같은 카드 결제창 흐름을 사용한다.

결제창 연동 흐름은 보통 다음 순서로 진행된다.

```text
API 키 준비
  → 결제창 호출
  → 결제 요청 결과 확인
  → 결제 승인
  → 결제 완료 응답 확인
```

<sub>출처: [4]</sub>

---

### 3단계. 카드 본인 인증

온라인 카드 결제에서는 카드 소유자가 맞는지 확인하는 인증 절차가 들어간다.

인증 방식은 카드사 앱 비밀번호, 지문 인증, 카드번호와 생년월일 입력, SMS 인증 등으로 진행될 수 있다.

쉽게 말하면 인증은 다음 질문에 답하는 단계다.

```text
이 체크카드를 쓰는 사람이 실제 카드 주인인가?
```

인증은 결제 승인 전 단계다.  
따라서 사용자가 인증을 마쳤다고 해서 결제가 최종 완료된 것은 아니다.

<sub>출처: [3]</sub>

---

### 4단계. 결제 인증 결과 반환

카드 인증이 끝나면 PG사는 결제 인증 결과를 가맹점 서버 또는 프론트엔드로 전달한다.

이때 전달되는 주요 값은 다음과 같다.

| 항목       | 설명                      |
| ---------- | ------------------------- |
| paymentKey | PG사가 발급한 결제 식별값 |
| orderId    | 가맹점의 주문 식별값      |
| amount     | 결제 금액                 |

이 단계에서 중요한 점은 **브라우저에서 돌아온 값만 보고 결제 완료 처리하면 안 된다는 것**이다.

결제 완료 처리는 반드시 가맹점 서버가 PG사의 승인 API를 호출하고, 승인 성공 응답을 받은 뒤 진행해야 한다.

<sub>출처: [5]</sub>

---

### 5단계. 가맹점 서버의 결제 승인 API 호출

가맹점 서버는 PG사에 결제 승인 API를 호출한다.

이 단계에서 PG사는 `paymentKey`, `orderId`, `amount` 등을 기준으로 결제를 검증하고 승인 처리한다.

온라인 결제에서는 다음 두 단계가 분리된다.

```text
사용자의 카드 인증 완료
  ≠
가맹점 서버의 결제 승인 완료
```

즉, 사용자가 카드 인증을 마쳤더라도 가맹점 서버가 승인 API를 호출하지 않으면 결제가 최종 완료되지 않을 수 있다.

<sub>출처: [5][6]</sub>

---

### 6단계. 카드사 승인 및 체크계좌 출금

PG사는 VAN 또는 카드사 네트워크를 통해 카드사에 승인 요청을 보낸다.

카드사는 다음과 같은 항목을 확인할 수 있다.

| 확인 항목      | 설명                                         |
| -------------- | -------------------------------------------- |
| 카드 상태      | 정상 카드인지, 정지 카드인지                 |
| 계좌 잔액      | 체크카드 연결 계좌에 결제 가능 금액이 있는지 |
| 이용 한도      | 일일 한도, 월 한도, 카드별 한도 등           |
| 거래 제한      | 해외 결제 제한, 온라인 결제 제한 등          |
| 본인 인증 결과 | 카드 소유자 인증이 정상적으로 되었는지       |

체크카드는 일반적으로 승인 시점에 연결 계좌에서 금액이 바로 출금된다.

다만 체크카드에 소액신용결제서비스가 연결되어 있다면, 잔액이 부족해도 일정 한도 안에서 결제될 수 있다.  
따라서 "체크카드는 잔액 부족이면 무조건 실패한다"고 단정하면 안 된다.

<sub>출처: [1][2][3][11]</sub>

### 7단계. 주문 결제 완료 처리

승인 API가 성공하면 가맹점 서버는 주문 상태를 결제 완료로 변경한다.

예시는 다음과 같다.

```text
PAYMENT_REQUESTED → PAYMENT_APPROVED
ORDER_PENDING → ORDER_PAID
```

이때 서버에는 최소한 다음 정보를 저장하는 것이 좋다.

| 저장 항목      | 이유                              |
| -------------- | --------------------------------- |
| orderId        | 내부 주문 식별                    |
| paymentKey     | PG 결제 조회 및 취소 식별         |
| 승인번호       | 카드 승인 식별                    |
| 승인금액       | 주문금액과 일치하는지 확인        |
| 결제수단       | 카드, 간편결제 등 구분            |
| 카드사 코드    | 카드 발급사 또는 매입사 구분      |
| 승인일시       | 결제 이력 기준                    |
| 결제 상태      | 승인, 취소, 부분취소 등 상태 관리 |
| 취소 가능 여부 | 부분취소 가능 여부 판단           |

PG사의 결제 식별값과 내부 주문 식별값은 반드시 함께 저장해야 한다. 나중에 결제 조회, 결제 취소, 환불, 장애 복구를 처리할 때 필요하기 때문이다.

### 8단계. 매입 및 정산

사용자 입장에서는 체크카드 승인 성공과 계좌 출금으로 결제가 끝난 것처럼 보일 수 있다.

하지만 가맹점 입장에서는 이후 매입과 정산 흐름이 이어진다.

매입은 승인된 결제 건에 대해 카드사에 대금 처리를 요청하는 과정이다.  
정산은 카드사 또는 PG사가 가맹점에 결제대금을 지급하는 과정이다.

즉, 체크카드 결제에서도 다음 두 흐름은 구분해야 한다.

```text
사용자 계좌에서 돈이 빠져나가는 흐름
  ≠
가맹점이 실제 정산금을 받는 흐름
```

<sub>출처: [3]</sub>

### 9단계. 취소 및 환불

체크카드 결제를 취소하면 사용자 입장에서는 이미 계좌에서 빠져나간 금액이 다시 입금되는 환불 흐름으로 이어진다.

카드 결제 취소는 매입 전인지, 매입 후인지, 부분 취소인지에 따라 환불 시점이 달라질 수 있다.

일반적으로 매입 전 취소는 비교적 빠르게 환불될 수 있지만, 매입 이후 취소나 부분 취소는 영업일 기준으로 시간이 걸릴 수 있다.

따라서 IT 시스템에서는 다음 두 상태를 같은 것으로 보면 안 된다.

```text
취소 요청 성공
  ≠
사용자 계좌 환불 완료
```

예시 상태값은 다음과 같다.

```text
CANCEL_REQUESTED
CANCELED
PARTIAL_CANCELED
REFUND_PENDING
REFUNDED
```

## 5. IT 관점 유의사항

### 5-1. 결제 금액은 서버 기준으로 검증해야 한다

결제 승인 API를 호출할 때 프론트엔드에서 전달된 금액을 그대로 믿으면 안 된다.

가맹점 서버는 내부 주문 DB에 저장된 주문금액과 PG 승인 요청 금액을 반드시 비교해야 한다.

```text
주문 DB 금액
  =
PG 승인 요청 금액
```

금액이 다르면 결제를 완료 처리하지 않고 취소 또는 실패 처리해야 한다.

KICC 개발자센터는 승인 결과의 결제금액과 상점의 결제금액이 다를 경우 반드시 취소 처리하라고 안내한다.

<sub>출처: [6]</sub>

---

### 5-2. 승인 성공 후 DB 저장 실패를 처리해야 한다

결제 승인 API는 성공했는데 가맹점 서버의 DB 저장이 실패할 수 있다.

이 경우 사용자의 체크카드 계좌에서는 돈이 빠져나갔는데, 쇼핑몰 주문은 결제 완료로 저장되지 않는 문제가 생긴다.

예시 흐름은 다음과 같다.

```text
결제 승인 성공
  → DB 저장 성공
      → 주문 결제 완료
  → DB 저장 실패
      → 결제 취소 API 호출
      → 주문 결제 실패 또는 취소 상태 저장
```

KICC 개발자센터는 승인 결과에 대한 상점 DB 처리 실패 시 반드시 취소 처리하라고 안내한다.

<sub>출처: [6]</sub>

---

### 5-3. 네트워크 타임아웃은 거래조회로 복구해야 한다

결제 승인 API를 호출했는데 응답 대기시간 초과나 네트워크 오류로 결과를 받지 못할 수 있다.

이때 무조건 실패로 처리하면 위험하다. 실제로는 카드사 승인이 성공했고, 체크카드 계좌에서 돈이 빠져나갔을 수도 있기 때문이다.

따라서 승인 요청 후 결과가 불명확하면 결제 조회 API로 실제 거래 상태를 확인해야 한다.

```text
승인 요청
  → 응답 없음 / 타임아웃
  → 결제 조회 API 호출
  → 승인 성공 확인
      → 주문 완료 처리 또는 취소 처리
  → 승인 실패 확인
      → 주문 실패 처리
```

KICC 개발자센터도 네트워크 오류나 응답 대기시간 초과 시 거래상태 조회를 통해 처리하라고 안내한다.

<sub>출처: [6]</sub>

---

### 5-4. 중복 결제와 중복 취소를 막아야 한다

사용자가 결제 버튼을 여러 번 누르거나, 네트워크 재시도로 같은 요청이 반복될 수 있다.

이때 같은 주문에 결제가 여러 번 승인되면 중복 출금 문제가 발생할 수 있다.

이를 막기 위해 다음 값에 유일성 제약을 둘 수 있다.

```text
orderId unique
paymentKey unique
idempotencyKey unique
```

멱등성은 같은 요청이 여러 번 들어와도 실제 처리는 한 번만 수행되도록 하는 방식이다.

예를 들어 같은 멱등키로 결제 취소 요청이 두 번 들어오면, 시스템은 두 번 취소하지 않고 첫 번째 요청과 같은 결과를 반환할 수 있다.

<sub>출처: [5][8]</sub>

---

### 5-5. 결제 상태 변경은 웹훅으로도 보완할 수 있다

결제 승인, 취소, 부분취소 같은 상태 변경은 API 응답만으로 관리하기 어려울 수 있다.

PG사는 결제 상태가 변경되었을 때 웹훅으로 가맹점 서버에 이벤트를 보낼 수 있다.

예시 이벤트는 다음과 같다.

```text
PAYMENT_STATUS_CHANGED
CANCEL_STATUS_CHANGED
```

웹훅을 사용할 때는 이벤트를 받는 즉시 무조건 상태를 덮어쓰면 안 된다.

현재 주문 상태와 이벤트 상태를 비교해서 유효한 상태 전이인지 확인해야 한다.

예시 상태 전이는 다음과 같다.

```text
PAYMENT_APPROVED → CANCELED 가능
PAYMENT_FAILED → CANCELED 불필요
CANCELED → PAYMENT_APPROVED 불가
```

### 5-6. 카드정보 저장은 최대한 피해야 한다

온라인 체크카드 결제에서는 카드번호, 유효기간, CVC 같은 민감정보를 직접 다루지 않는 구조가 안전하다.

PG 결제창을 사용하면 카드정보 입력과 인증은 PG사 또는 카드사 영역에서 처리되고, 가맹점 서버는 `paymentKey`, `orderId`, 승인 결과 같은 결제 식별 정보만 저장하는 방식으로 설계할 수 있다.

PCI DSS는 결제 계정 데이터가 저장, 처리, 전송되는 환경을 보호하기 위한 보안 요구사항이다.  
또한 거래 승인 이후 카드 검증 코드, 즉 CVC/CVV 같은 값을 저장하는 것을 금지한다.

토스페이먼츠 Core API도 카드번호 결제 API는 별도 리스크 검토와 추가 계약 후 사용할 수 있으며, 구매자의 카드번호를 저장해 사용할 수 없다고 설명한다.

## 6. 체크카드 온라인 결제에서 특히 봐야 할 차이점

| 구분        | 신용카드                                   | 체크카드                                    |
| ----------- | ------------------------------------------ | ------------------------------------------- |
| 결제 재원   | 신용한도                                   | 연결 계좌 잔액                              |
| 승인 시점   | 한도 차감                                  | 계좌에서 즉시 출금                          |
| 청구 사이클 | 이용기간 후 결제일 청구                    | 일반적으로 승인 시점 출금                   |
| 잔액 부족   | 신용한도 안이면 승인 가능                  | 일반적으로 실패                             |
| 예외        | 할부, 리볼빙 등                            | 소액신용결제서비스 가능                     |
| 취소        | 청구 전/후에 따라 청구 반영 달라질 수 있음 | 이미 출금된 금액의 환불 흐름으로 이해 필요  |
| IT 핵심     | 한도, 청구, 매입취소                       | 즉시출금, 환불상태, 잔액부족, 소액신용 여부 |

체크카드는 카드 이용 즉시 결제된다는 점에서 신용카드와 다르다.

다만 체크카드 소액신용결제서비스처럼 잔액 부족 시 일정 신용한도 안에서 결제되는 부가 서비스도 존재하므로 상품별 예외를 고려해야 한다.

## 7. 구현 예시 상태값

```java
public enum PaymentStatus {
    READY,              // 주문 생성, 결제 전
    AUTH_REQUESTED,     // 결제창 인증 요청
    AUTH_COMPLETED,     // 인증 완료, 승인 전
    APPROVE_REQUESTED,  // 서버 승인 요청
    APPROVED,           // 승인 완료, 체크카드 출금 완료로 볼 수 있음
    APPROVE_FAILED,     // 승인 실패
    CANCEL_REQUESTED,   // 취소 요청
    CANCELED,           // 전체 취소
    PARTIAL_CANCELED,   // 부분 취소
    REFUND_PENDING,     // 환불 대기
    REFUNDED            // 환불 완료
}
```

실제 PG 응답 상태와 내부 주문 상태는 분리해서 관리하는 것이 좋다.

PG 상태는 외부 결제기관 기준 상태이고, 주문 상태는 쇼핑몰 내부의 상품 지급, 배송, 재고 차감과 연결되기 때문이다.

## 9. 질문과 답변

### Q1. 체크카드 온라인 결제는 신용카드 결제와 흐름이 완전히 다른가?

완전히 다르지는 않다.

온라인 카드 결제라는 큰 흐름에서는 인증, 승인, 매입 단계를 거친다. 다만 승인 시점의 효과가 다르다.

신용카드는 한도만 차감되고 나중에 청구되지만, 체크카드는 승인 시점에 바로 출금된다.

<sub>출처: [3]</sub>

---

### Q2. 사용자가 인증을 마치면 바로 결제 완료인가?

아니다.

인증은 카드 소유자 확인 단계이고, 최종 결제 완료는 가맹점 서버가 PG사의 결제 승인 API를 호출해 성공 응답을 받은 뒤 처리해야 한다.

<sub>출처: [5][6]</sub>

---

### Q3. 체크카드 결제 승인 후 DB 저장이 실패하면 어떻게 해야 하는가?

승인은 성공했지만 상점 DB 저장이 실패하면 결제는 되었는데 주문은 결제 완료가 아닌 상태가 될 수 있다.

이 경우 결제 취소 API를 호출하거나, 거래 상태를 조회한 뒤 보상 처리를 해야 한다.

KICC 개발자센터는 승인 결과에 대한 상점 DB 처리 실패 시 반드시 취소 처리하라고 안내한다.

<sub>출처: [6]</sub>

---

### Q4. 체크카드 취소는 바로 환불되는가?

항상 바로 환불된다고 단정하면 안 된다.

카드 결제가 매입되기 전에는 취소 직후 환불될 수 있지만, 매입 이후 또는 부분 취소는 영업일 기준으로 시간이 걸릴 수 있다.

따라서 시스템에서는 `취소 완료`와 `환불 완료`를 구분하는 것이 안전하다.

<sub>출처: [7]</sub>

---

### Q5. 체크카드 결제에서 카드번호를 직접 저장해도 되는가?

일반적인 쇼핑몰 서비스라면 저장하지 않는 방향이 맞다.

PCI DSS는 결제 계정 데이터 보호를 위한 보안 요구사항을 정의하고, 거래 승인 이후 CVC/CVV 같은 카드 검증 코드 저장을 금지한다.

PG 결제창을 사용하면 카드정보 입력과 인증은 PG사 또는 카드사에서 처리하고, 가맹점 서버는 결제 식별키와 승인 결과 중심으로 저장하는 구조를 만들 수 있다.

<sub>출처: [5][10]</sub>

## 10. 조사 후 정리

체크카드 온라인 결제는 온라인 카드 결제의 일반 흐름인 인증, 승인, 매입 단계를 따른다.

다만 체크카드는 신용카드와 달리 승인 시점에 연결 계좌에서 금액이 바로 출금된다는 점이 핵심이다.

IT 구현 관점에서는 결제창 인증 결과만으로 주문을 완료하면 안 되고, 서버에서 결제 승인 API를 호출한 뒤 성공 응답을 기준으로 주문 상태를 변경해야 한다.

또한 금액 불일치, 승인 후 DB 저장 실패, 네트워크 타임아웃, 중복 요청, 취소/환불 지연 같은 예외 흐름을 별도로 설계해야 한다.

보안 관점에서는 카드번호와 CVC/CVV 같은 민감정보를 직접 저장하지 않는 구조가 안전하다. PG 결제창을 사용하면 카드정보 입력과 인증은 PG사 또는 카드사 쪽에서 처리하고, 가맹점 서버는 결제 식별키와 승인 결과 중심으로 저장할 수 있다.
